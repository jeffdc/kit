## What was built

### Summary

mull done <phase-id> now files a phase's integration review, the step the integration-review flag (8817) left open. Run by the supervisor in a clean worktree at the tip of the phase's plan's target, it runs the hard checks there, writes reports/<phase-id>-<n>.md with the phase's done items and their combined diff, and files a review entry carrying phase and items. Accepting that review (by its entry or the phase ID) completes the phase; do --reason adds a committed fix-up item to the phase, which reopens it until a new review covering the fix-up is accepted. mull report <phase-id> prints the report, Needs you shows the review on its phase (row phase/phase_title, and the phase page's needs_you), and the make dev demo now files one for Design pass. design.md, json.md and the supervisor guide (a new Integration reviews section) document it; the agents guide is unchanged, since only the supervisor runs it.

## How it was built

### Design notes

Shape. The new code is in internal/mull/phase_done.go so it stays clear of done.go, which parallel workers touch: PhaseDone, the refusal rules (phaseDoneItems), the target-tip check, the combined diff scope, the send-back (sendBackPhase) and the accept gate (acceptPhaseReview). cmd's done calls a small Finish(id) that dispatches to Done or PhaseDone by what the ID names, so the item path is untouched. done.go only gained shared pieces: doneText (the summary and design checks both use), diffChanges (the old changes body, now with an optional literal pathspec list), a Phase flag on ErrChecksFailed for its message, and renderReport/ReportText branches for a phase report (an Items section, no decisions section, a line naming the combined diff's range).

Model. Report gains phase and items ([{id, title}]) and item becomes omitempty, so a phase report is stored at reports/<phase-id>-<n>.md: IDs are unique across phases and items, so the path, the dataPaths pattern and the report listing all work unchanged. The review entry uses the Phase and Items fields 8817 already defined, so whether a phase is reviewed stays derived (awaitsIntegrationReview) and nothing new is stored on the phase.

Combined diff. A plain base..tip diff on a busy target would carry every other plan's work, so it's limited to the files the phase's items' latest done reports changed, from the merge base (--octopus) of their claim bases to the tip. Other work on those same files does show, which is what an integration review should see. Rejected: unioning each item's own diff (shows pieces, not how they fit) and walking trailer commits (costly, and misses merge resolutions).

Rules. Refused (invalid_state) without the flag, with open work or nothing done, when an accepted review already covers it, or while one is open or parked (one at a time); and unless HEAD is the target's tip, branch or detached. Failed checks save the report and file nothing (checks_failed). A tour is required when the combined diff touches UI files, as for items. Accept by entry or phase ID, with the self-accept gate keyed on the worktree that filed it. do --reason titles the fix-up by the reason's first line (cut to 80 runes at a word), keeps the whole reason in its notes, sets from to the review, and refuses --as phase or a --plan/--phase that disagrees. The do result carries only the new item, so a batch @ref names the fix-up.
