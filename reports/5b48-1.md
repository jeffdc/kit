## What was built

### Summary

mull serve has a read-only JSON API for every page of the UI: GET /api/projects/{id} (overview: title-block summary, tab counts, Needs you ranked in six tiers, and each plan's Built / Now / Next / Go live / Agents), /tree (the sheet index), /plans/{slug} (phase schedule in steps, needs you, what's next, the doc and the status of every phase or item it names), /phases/{phase}, /items/{item} (with the review packet: latest report, each carried decision's current settlement, report history), /unplanned and /backlog (?plan=slug|none, with filter facets). The ranking and now/next/go-live logic are methods in internal/mull with unit tests; internal/serve only resolves the project and maps errors (404 not_found, else 500). The project list summary gains blocking. Documented in mull guide json.

### UI tour

## How it was built

### Design notes

Shape: the logic is three files in internal/mull, each a read of one snapshot (m.view), so every number on a page is consistent while agents write. needsyou.go is the ranking; schedule.go is phase state, now/next, go live and the plan schedule; pages.go is one exported method per page (Overview, TreePage, PlanPage, PhasePage, ItemPage, UnplannedPage, BacklogPage) and the row types they share (ItemRow, PhaseRow, AgentRow, DocRef). internal/serve/api.go is one helper that resolves the project (resolve.go, the shared file), opens it, calls the method and writes JSON or the error; registered from Handler with the one agreed line.

Ranking: entries have no phase, so a question's place comes from its item. Active work, or committed work that's ready (phase needs done, plan not shaping, as ItemView.Ready already says), is blocking; otherwise by whether the item's phase has its needs done (now) or not (later); no item, or an item in no phase that isn't ready, is the plan tier, which also takes project-wide questions. That follows the prototype's tierOf, where committed work in a waiting phase is a later-phase question since it can't start anyway. Tiers carry a fixed rank 1-6 so the UI can number them; title and hint are in Go so the copy lives beside the rule. Decisions group by item, else source, else plan, else project; a group carried by an open review names it rather than hiding the decisions. Parked entries are counted, retired kinds never shown.

Now/next/go live: phaseState is done (phaseComplete, the existing definition), now (needs satisfied, plan not shaping) or waits. Next is a waiting phase one step away. The model has no go-live marker, so go live is derived as the unique deepest phase when deeper than one step; I asked the human (cc78) whether to add a marker, because the prototype's taxogall shows a phase after go live that no derivation can recognise. The schedule groups unfinished phases by depth of needs not yet done, so step 0 is exactly "can start now".

Summary: I extracted Summary's body into m.summary(s) so the overview reuses it inside its own snapshot, and added Blocking (the first tier's count). Board is untouched.

Cost: readGit (every local branch) is used only by the overview, plan and item pages, where commit counts show; about 0.3 s on kit. The others read records only (about 50 ms). Measured against kit's real mull branch with a throwaway server built through a go build -overlay from the scratchpad (nothing added to the repo).

Review packet: the latest report, with each carried decision's current settlement and the review entry only when it was filed for that report, so a send-back followed by a failed attempt shows the failed attempt, not the stale packet.

Rejected: putting go live on the model (a model change for the human to decide); a generic /api/projects/{id}/records dump with logic in JS (the item asks for the logic in Go); per-tier endpoints (one request per page is simpler and consistent).

Not done here, by design: last-looked and revisions (3deb), SSE (35f5).

### Decisions made in the session

Accepting the review ratifies these. To decide one differently, before accepting: `mull decide <id> "..."`

- **2ff3** Decisions to approve group by the item they were made in, else their source text, else their plan, else the whole project; a group carried by an open review names it, and carried decisions stay listed in the decide tier
  Why: Agents record decisions with --item, so the item is the real source. Keeping carried decisions listed means nothing open is hidden; the review pointer lets the UI say accepting the review ratifies them
- **8ff0** Needs you places a question by its item: active or ready committed work is blocking; otherwise now or later by whether the item's phase has its needs done; no item, or an item in no phase that isn't ready, is the plan tier (project-wide questions included)
  Why: Entries have no phase field, so the item's phase is the only phase signal. Follows the prototype's tierOf: committed work in a waiting phase is a later-phase question, not blocking, since it can't start anyway
- **c91f** Go live is derived: the one phase deepest in its plan's needs, when deeper than one step; no stored marker. A flat plan or one ending in several phases has none
  Why: The model has no go-live field and the item is read-only; this matches 'go live needs X, Y, Z' for plans that converge. Asked whether to add a marker
- **8897** The API is one endpoint per page under /api/projects/{id}: the overview at the project's own path, plus tree, plans/{slug}, phases/{phase}, items/{item}, unplanned and backlog (?plan=slug|none); each page is read from one snapshot of the mull branch
  Why: One request per page keeps the UI simple and every number on a page consistent while agents write. The tree endpoint (sheet index) was added because the rail is on every page and no other endpoint lists every phase and item
- **4466** The overview, plan and item pages read commit links (as mull view does) for agents' commit counts and an item's branches; the tree, phase, unplanned and backlog pages read records only, and their item rows carry the claim but no commit counts
  Why: Reading commit links walks every local branch, about 0.3 s on kit; it's paid only where commits are shown (the Agents line, the item page). The other pages answer in about 50 ms
- **6138** A plan's schedule is the done phases first, then one step per depth of needs not yet done: now (step 0), then, and go_live for the step holding the go-live phase
  Why: Grouping by remaining depth makes step 0 exactly 'can start now', and done phases stop pushing later ones down; the prototype's 'Built before mull' group becomes Done since real data has no prior phases
- **36a0** The review packet is the item's latest done report, with each carried decision's current settlement, and the review entry only when it was filed for that report
  Why: After a send-back and a failed attempt the latest attempt is what matters; showing the older packet would mislead. The report list gives the history
- **a515** API errors: not_found is 404; anything else, an unreadable registered project included, is 500 with its mull code
  Why: The code says what's wrong; the status only needs to separate a bad URL from a broken repo
- **ad17** Doc refs: any 4-hex word in a plan or phase doc that names a phase or item is listed with its status, in order of first mention, for the doc's status margin
  Why: Real docs name phases by bare ID (the prototype's {{id}} also matches); a word that happens to look like an ID but names no record is ignored
