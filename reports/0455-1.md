## What was built

### Summary

Triage: captured items gain a triaged stamp. mull triage <id...> --on-request (or --all [--plan slug|none]) stamps them; untriaged = captured with no stamp, counted in every Progress (untriaged), project-wide in view.untriaged with view.last_triage, and listed by list --untriaged. Captured items can be tagged without committing: set <id> plan <slug|none>, set phase across plans for captures, and set category. mull guide triage is the procedure an agent runs with the human. JSON documented in guide json.

## How it was built

### Design notes

The stamp lives on the item: model.Item gains `triaged` (omitempty, so existing records and their YAML are unchanged). Untriaged is derived, never stored: captured and no stamp (graph.go `untriaged`). A per-item stamp makes "captured since its last triage" exact without a project- or plan-level record, and the project's last triage is just the latest stamp, so nothing new needs migrating or syncing.

`mull triage` is one op (TriageIn in ops.go, fields = flags: ids, all, plan, on-request) with one implementation (`triage` in work.go) used by the CLI and batch. It requires --on-request, like commit and plan agree, because stamping hides items from the human's untriaged count. IDs are strict (must be captured items) so typos and stale lists fail; --all stamps every captured item in scope, with --plan <slug|none> narrowing it. Rejected: a lenient form that silently skipped non-captured IDs (hides mistakes), and a plan-level "last triaged" time (can't express "these three, not that one").

Counting: Progress gains `untriaged` next to `captured`, so every board, phase line, unfiled line and plan list/show carries it with no new board fields; the view adds project-wide `untriaged` and `last_triage`. Text view shows "N captured (M untriaged)" and a BACKLOG line pointing at the guide. `list --untriaged` gives the list when an agent needs one.

Tagging without committing (loose end b3e5) extends `set` rather than adding a `tag` command: `set <id> plan <slug|none>` for captured items (a new plan clears the phase), and `set <id> phase <id>` across plans moves a captured item's plan. `set` is already the per-field op with a batch form, so a triage batch mixes commit, set, drop and triage lines in one commit. Committed work still can't change plan through set: that would bypass the shaping-plan rule 1b81 adds to commit/add. `set <id> category` was added because triage tidies categories and there was no way to change one.

The guide (internal/guide/triage.md) is the procedure: list untriaged, propose per item, settle (commit / tag / start / drop / leave) on the human's word, then stamp what you went through, with a batch example. Tests: internal/mull/triage_test.go (stamping rules, counts, text, retagging, batch), a CLI test, and the shapes test for the new JSON.
