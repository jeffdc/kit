### Summary

They're kept on the plan record, and plan show and plan list include them. At done, the report's changed files are matched against the item's plan's globs, and the matches go in the report's new shared list ({status, path, glob}). ## How it was built

### Design notes

Shape: a plan field plus a pure function at done time. model.Plan gains Shared []string (yaml/json "shared", omitempty), set by Mull.PlanShared / planShared in done.go beside planChecks. It trims, drops blanks and repeats, refuses a glob with a leading / or ./ (invalid_argument: a rooted glob would never match a diff path), and writes nothing when the list is unchanged. It's exposed as `mull plan shared <slug> [glob...]` and as the batch op "plan shared" {slug, globs}. It takes no --on-request gate. design.md already explains why checks are gated and doc/rules aren't: checks decide whether work gets through, and shared globs only flag it.

At done, sharedChanges(changes, globs) reuses globRegexp, the matcher config layers already use, so there's one glob dialect. It walks the files already gathered for Changes by layer (no extra calls), so renames match on their new path, as layers do. It records {status, path, glob} for the first glob each file matches, sorted by path. It runs inside the done update transaction against s.plans[i.Plan], so it uses the globs as they are when the report is written. The report keeps its own copy, so later edits to the globs never rewrite an old review. An unplanned item has no plan, so it gets nothing, and there's no config fallback (the same choice as preview, decision 0087). renderReport adds a one-line count under the status block, so it's seen first, and a "Shared files changed" list before Changes by layer. Both appear only when something matched, because the report doesn't know whether the plan had globs at all.

Review UI: item.js builds a .shared box (1px ink border, label and count, a muted line, one grid row per file with the glob muted) between the design notes and the decisions, and adds a muted "shared" to the matching rows in Files by layer. DESIGN.md's One Mark, One Job Rule says to use ink and grey, as the overlap does: this needs a look, not an answer. I checked the rendering by importing item.js in node with a stub page. The plan sheet doesn't list the globs. The item asked for the review only, and plan show carries them.

Change feed: planChange reports "shared" as a short field (space-joined), since glob lists are short and from/to is useful. json.md documents it.

Demo: the web plan sets shared globs, and the Digest job now works on its own branch and changes app/layout.css, so its packet shows the flag. That branch is what web-next merges later, replacing the empty commit. The digest's work is on web-next, so the account/theme overlap demo is unchanged. I seeded it once into a scratch dir and checked the stored report.

Rejected: parsing globs out of the rules markdown (fragile, and the item names a command); per-file flags inside LayerChanges (it would widen a long-stable shape, and a separate list is easier to read and to count); a soft warning in done's output (the report is where the review looks).

No read path changed (done is a write, and plan show and report just carry the new field), so no make bench. Tests: plan_shared_test.go covers flagging with two globs, no globs, no match, the set/clear/refuse/no-op write, and the batch op with its change-feed field. shapes_test covers plan shared's output and report.shared[0]'s keys. make test passes.
