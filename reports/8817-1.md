## What was built

### Summary

A phase can now require an integration review. mull phase set <id> integration-review on|off sets it; it's Jeff's call, so agents need --on-request through phase set or set. With it on, a phase whose items are all done or dropped isn't complete. It shows awaiting integration review (phase state awaiting-review) and the phases that need it stay blocked, until an accepted integration review covers every done item in it. That review is an inbox review entry carrying the phase and the items it covers, new Entry fields that 8e3e's mull done <phase-id> will file. A fix-up or follow-up done later reopens the gate. mull view, mull context, the plan and phase pages, the tree and the dev demo all show the state. docs/design.md, the agents and supervisor guides (and kit's AGENTS.md), mull guide json and DESIGN.md are updated.

## How it was built

### Design notes

The flag is a bool on the phase record (integration_review, omitempty, so phases without it are unchanged on disk). Whether the review is accepted is derived from the inbox, never stored. That fits mull's rule that status comes from records, and it means accept, do and park need no phase-specific writes for 8e3e. An accepted review entry whose new phase field names the phase counts only if its new items field covers every done item in the phase. I chose coverage over "the latest review is accepted" or comparing timestamps because items carry no finish time. With coverage, a fix-up made by do --reason, a follow-up, or a capture committed later all reopen the gate once they're done, and dropped items need none.

In graph.go, phaseComplete is split into phaseBuilt (the old rule: every committed item done or dropped, and at least one) and awaitsIntegrationReview. phaseComplete is now built && !awaits, so everything that went through it (needs being satisfied, readiness, depth, rank's phase order, the board sort, search's finished flag) honours the gate with no further change. awaitsIntegrationReview returns false straight away for an unflagged phase, so the entry scan only happens on flagged phases. PhaseView gains awaiting_integration_review, and PhaseRow/PhaseRef gain the state awaiting-review. phaseState returns it ahead of waits, so a phase that is built but has a need added later still reads as awaiting review.

Schedule and status: awaiting phases get their own schedule group (key review, step 0) right after Done, rather than sitting in "Can start now". PlanStatus.now includes them, since they're the live work for the supervisor and Jeff and the plan page's What's next is built from now, and they don't count toward built. A waiting phase whose need is awaiting review counts as next. The text view says "awaiting integration review" where it would say "complete", and context's phase progress line gets " · awaiting integration review".

The setter: a new phase set op and CLI command (title, summary, integration-review), with on-request, mirroring plan set. m.set's phase branch now goes through setPhase. Plain mull set accepts the field too, but it has no --on-request flag, so for an agent it's refused with a pointer to mull phase set ... --on-request, while Jeff's own writes (AsHuman) pass. The value must be on or off. Setting it to its current value writes nothing, as plan checks does. I didn't add the toggle to mull serve's op list, since the item didn't ask for UI editing. The revision feed records integration_review as a short field (on or empty).

UI: there's a new stage label and style (the review double border) for awaiting-review. The tree, plan table and plan card treat it as live, not dimmed. The phase sheet gets an Integration review row and an explanatory line. The dev demo gets a Design pass phase with the flag on and its item accepted and merged into web-next, and Launch needs it.

Rejected: storing a reviewed timestamp or item list on the phase, which would have needed accept to write the phase and is state the inbox already holds. Also rejected: treating Entry.Item as the phase ID, which would muddle every place that reads Item as an item.

Bench (make bench's run step on the large seed, in-process ms, main before then after): load 276.5 then 270.7, overview 46.1 then 43.8, tree 19.5 then 16.9, board 38.1 then 36.7, plan metrics-23 30.6 then 29.8, phase 06fe 15.8 then 14.8. Process counts per page are unchanged. The read path costs nothing measurable for unflagged phases.
