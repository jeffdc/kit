## How it was built

### Design notes

How: the server doesn't reimplement anything. Batch's run loop became runBatch(lines, bad, dryRun, since); Batch passes since "" and Apply passes the page's commit, so a page's write is exactly a mull batch, one commit, all or nothing, with @refs and per-line errors.

The human: Mull gains an optional human name (AsHuman reads the repository's git user.name and refuses when unset). settle records By = name, Human = true, OnRequest = false; the six human-only checks (plan new, plan agree, commit, triage, promoting an idea, self-accept) go through asked(onRequest), which also passes for the human. A new Settlement.Human field, rather than a name in By alone, because By is otherwise a worktree path and nothing else could tell them apart.

Stale pages: inside the write transaction, after the ops ran, unchangedSince diffs the records between the page's commit and the commit the transaction read (recordChanges, the same diff the revision schedule uses) and refuses if any changed record is named by an op (refFields, after refs resolve) or written by this transaction (new Tx.Written). Because it runs inside store.Write, a CAS retry re-checks against the new tip. It runs before the failed-lines check, since a change is the likely cause of a failure (e.g. already settled).

The commit: store.Update became a wrapper over store.Write, which returns the commit written, so Apply can report it; 07e4 needs it to acknowledge exactly the acting commit.

Policy stays in the server: uiOps (accept only) and refusing on-request live in internal/serve/ops.go, mull itself stays policy-free. writeMullError now maps batch_invalid 400, conflict 409, busy 503.

Docs: json.md (endpoint, settled.human, decisions.human, conflict code, status codes, not_allowed cases), design.md's mull serve section, README, the serve package comment.

Tested in internal/mull/apply_test.go (attribution, human-only steps, stale pages by name and by write, input errors) and internal/serve/ops_test.go (the endpoint and every refusal); also run end to end against a built binary in a scratch repo: approved by jeffdc with human true, the retry 409.

### Decisions made in the session

Accepting the review ratifies these. To decide one differently, before accepting: `mull decide <id> "..."`

- **2003** A settlement the human makes from mull serve records by: <git user.name> and human: true (a new optional field on settled and in the decision log), with on_request false
  Why: By alone can't tell a name from a worktree path; the flag says the human made it without saying via what, as asked.
- **4f8b** Mull.Apply (and store.Write) return the commit the write made, and POST …/ops returns it as commit
  Why: 07e4 needs the acting commit to acknowledge what was touched, and it's exact only from inside the write.
- **6e24** A write from a page conflicts when any record its ops name by ID, or write, changed since the commit the page showed; a named plan or phase counts even when it is only where an item goes
  Why: Over-strict on purpose: a refused write costs a redraw and a retry, acting on what the page no longer shows could be wrong. The conflict is reported ahead of failed lines, as it is likely why they failed.
- **869a** The UI's op allowlist starts as accept only, and each later step adds its own ops; on-request in a page's op is refused (400), never ignored
  Why: The plan doc says only the ops the UI offers; 92eb is the next consumer and needs only accept.
- **f292** Write errors map to HTTP: invalid_argument and batch_invalid 400, not_allowed 403, not_found 404, conflict 409, busy 503
  Why: batch_invalid and busy were 500 before; no endpoint returned them until now.
