## How it was built

### Design notes

Four small, independent fixes, one commit.

1. Merge commits after acceptance. `readGit`'s `afterAccept` closure now returns early for any commit with more than one parent, before looking at its trailers. That's the one place both the target walk and the other-branches walk count work after acceptance, so both are covered. A non-merge commit after acceptance still counts (tested). Rejected: matching the merge's subject ("Merge branch 'main' into …"), since subjects vary and a merge with an edited message or a trailer is still a merge.

2. Worktree prune order. `branchHeads` became a thin wrapper over a new `branchRefs`, whose single `for-each-ref` now also reads `%(upstream)`, keeping only local upstreams (`refs/heads/…`). `readGit` keeps them on `gitState.upstream`, so `mull worktrees` and the view learn each branch's tracked branch with no extra git call. In `worktreeRows`, the list of branches to delete is built by a small recursive `list(b)`: skip empty/HEAD, already listed, protected (targets, release, mull), missing, or checked out in another worktree; otherwise list its upstream first, then it. It runs for the checked-out branch, then the claim branch, so a harness's worktree branch that the item branch tracks comes out first, and the item branch's `git branch -d` then measures against HEAD (the target checkout) instead of refusing against an upstream that's behind it. Upstreams join `branches`, so the existing "every listed branch is on the target" test (Merged) covers them: an unmerged tracked branch makes the worktree not prunable rather than producing commands that would fail. The new test runs the commands it gets, in order, in the temp repo and checks both branches are gone. The harness branch is found only through git's tracking config, never by name, to keep mull harness-neutral; a harness branch the item branch doesn't track (the item branch made from main without tracking) still can't be linked and is left alone.

3. Revision schedule link. `target()` in `web/revision.js` now sends `plan_doc` and `plan_rules` changes to `#/<pid>/plans/<slug>/doc` (the Plan doc tab, which shows the doc and then the rules); a `plan` record change still goes to the Status tab. Phases have no tabs, so they're unchanged. Checked by importing the module in node and rendering a schedule with all three kinds.

4. Shared globs in context. `ContextItem` gained `Shared []string` (`shared`, omitted when empty), filled from the item's plan beside `plan_rules` and `preview`. Unplanned work has none. Not added to the brief plans list, which stays compact. The output shapes test lists the key.
