# Done report 1: Accept or send back a review from its packet (db04)

**Status:** PASSED

## What was built

### Summary

Reviews are settled from their packet in mull serve: Accept saves as the human and, while armed, names each decision it will ratify; Send it back takes a reason in place and sends the item back with it in its notes. The server now offers do.

### UI tour

1. Open an item in review (Needs you, Waiting for your review, then Review).
2. Click Accept: it turns ink and asks "Accept and ratify N?", and a line under the header names each open decision it will ratify; Esc cancels.
3. Click it again: a toast says it was accepted and how many decisions were ratified, and the header shows ACCEPTED with the time; the item is done and leaves Needs you.
4. On another review, click Send it back: a form opens under the header; write what's wrong and save. The header shows SENT BACK with your reason, the reason is in the item's notes, and the item is committed again.

### Checks (run by mull)

- `make done-checks`: pass, 3.3s

## How it was built

### Design notes

How: item.js's review() uses the two write kinds from write.js. Accept is writeButton (accept on the item, which settles its review and ratifies what it carries); Send it back is textWrite (do on the review entry, the reason as its field). While Accept is armed, writeState(key).armed adds a note under the header naming each open decision with its ID and text; the failure line and the send-back form sit there too, so everything about the header's actions appears right under it.

Server: uiOps offers do. A test puts an item through mull done with a carried decision (helper inReview) and sends it back (committed, reason in notes), then accepts another (done, the carried decision settled by the human).

Found on the way: the copied command this replaces was mull do <item>, but do takes an inbox entry ID, so it failed; the write uses the review entry.

Docs: DESIGN.md gains a Review packet component; the model sheet, READMEs and json.md name the new writes.

Checked in headless Chromium on a scratch repo: Accept armed lists the carried decision, saving shows ACCEPTED; Send it back with a reason shows SENT BACK and the reason in the notes. (A first run looked like the first click didn't arm; it had clicked before the item sheet loaded, and a timed trace showed the arm holding.)

### Decisions made in the session

Accepting the review ratifies these. To decide one differently, before accepting: `mull decide <id> "..."`

- **703b** Accepting a review names the decisions it will ratify while armed (a line under the header), rather than in a dialog or always
  Why: The phase doc asks the page to say which before it writes; the armed state is the moment of asking, and the packet already lists them below.
- **8015** The server offers do in full (it also turns questions into items and promotes ideas), not only for reviews
  Why: All of do is a step the human takes; narrowing it per kind would put mull policy in the server. The page only offers it for reviews today.
- **b9bd** Send it back runs do on the review entry, not the item
  Why: do takes an inbox entry; the copied command it replaces passed the item ID and would have failed.
