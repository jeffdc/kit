## What was built

### Summary

mull serve's reads come from a cache of parsed states keyed by mull commit, so a page whose data hasn't changed costs one rev-parse plus the page's own work. A new commit (after any write) is read as a diff from the last one: only changed files are read and parsed. Git history for the board is cached by commit ID (one for-each-ref per read), and lookups the pages lean on (items by phase; Tx.List) no longer scan everything per item. make bench, large seed (5000 items, 27k commits), median over HTTP: overview 650->49ms, tree 587->53ms, backlog 487->36ms, plan 624->35ms, phase 479->25ms, item ~520->32ms; first read after a write ~480->32ms. kit: every page 17-35ms over HTTP, from 65-130ms. Revision and the project list (which computes revision) are unchanged: phase 4.

## How it was built

### Design notes

Four layers, each measured with make bench before the next.

1. State cache (internal/mull/cache.go). A generic LRU (8 states) keyed by commit, with single-flight loading so a page's burst of first requests shares one load, and failed loads not kept. view() and stateAt() read through it; update()/write() don't, since a write needs a mutable state of the latest tip inside the compare-and-swap. Because the cached state is shared across requests and goroutines, it's guarded rather than trusted: store.ReadOnly gives a Tx that panics on Put/Delete; Inbox, the one read API that returned the state's own record pointers, now returns copies; and TestReadsDontChangeTheCachedState fingerprints every record around every read API (including a caller scribbling on Inbox results) and compares the cache with a fresh parse. I checked that the test fails when the Inbox copy is removed. TestConcurrentReadsShareAState runs pages concurrently under -race.

2. Git cache (links.go, summary.go). readGit and summaryRefs used 4-7 git calls per page: rev-parse of the integration branch, a 5000-commit log, rev-parse of release, rev-list --count, for-each-ref and a log per other branch. Now one for-each-ref returns every tip, and logs/counts/commit times are memoised by the commit IDs they read (logFrom), which can never change. Rejected: keying gitState by the whole set of refs, which would recompute everything when any branch moved.

3. Indexes. After 1 and 2 the large tree still took 138ms; the profile showed phaseItems sorting all 5000 items once per item (itemView -> blockedBy -> satisfied -> phaseComplete). Items by phase are now built once when a state enters the cache (state.index). Only read-only states get it: in a write a record's phase can change before putItem, so the write path keeps the live scan. Callers get a clone. Separately, store.Tx.List scanned and sorted every path per call (latestReport per item); on a snapshot with no writes it now binary-searches sorted paths computed once (sync.Once, since snapshots are shared).

4. Incremental reload. A full read and parse of the large branch is ~480ms, paid on every first read after a write. Snapshots now keep blob IDs; ReadOnly(commit, prev) uses diff-tree against the previous commit and reads only changed blobs, and loadFrom reuses a previous record pointer when its blob (and its doc's blob, for plans and phases; and its directory, for format 1 phases) is unchanged. Sharing record pointers between states is safe because both are read-only. TestIncrementalLoadMatchesFresh compares incremental and fresh states after every kind of write (new records, changed ones, docs written and removed, reviews, settlements); I checked it fails if plan reuse ignores the doc.

Preload(commit) is exported for make bench's new 'next commit (after a write)' target; it takes only full commit IDs, because the cache key must not be a moving ref.

Not done here: revision and the project list (phase 4, 159f), and the tree/unplanned pages still carry every done item (phase 3).

### Decisions made in the session

Accepting the review ratifies these. To decide one differently, before accepting: `mull decide <id> "..."`

- **0dc4** mull.Preload(commit) is exported, taking only full commit IDs, so make bench can time the first read after a write
  Why: The cache is keyed by commit, so a ref name would alias a moving target; refusing anything but an ID keeps the key honest.
- **2ee9** Git history used by the board is cached by commit ID: one for-each-ref per read gives every branch tip, and logs and counts are keyed by the IDs they read
  Why: git log of a commit ID never changes, so pages went from 4-7 git calls to 1-2 with no invalidation to get wrong. Caveat: a shallow clone deepened later keeps the shorter cached log until it falls out of the LRU.
- **3dd3** Lookups (items by phase) are built only for read-only states, when they enter the cache; a state being written keeps scanning
  Why: In a write a record's phase can change before putItem, so an index there could go stale mid-transaction. phaseItems sorted every item once per item: 70% of the tree and overview time on the large seed.
- **8363** A cached state is guarded, not trusted: its transaction panics on writes, Inbox returns copies, and a test fingerprints the cached records around every read API
  Why: A shared state changed by one read corrupts every later one; the fingerprint test was checked to fail when Inbox handed out its own records.
- **8587** Reads share parsed states in a process-wide LRU (8 states) keyed by mull commit; writes keep loading fresh inside their compare-and-swap
  Why: A commit names its content exactly, so a cached state can't be stale; one rev-parse per read finds the tip. Writes need a mutable state of the latest tip, so they stay as they were.
- **98cb** A new commit is read as the difference from the last state loaded for that repository: diff-tree for the changed files, and records whose blobs (and docs' blobs) are unchanged are reused
  Why: The first read after a write on the large seed went from ~480ms (a full read and parse) to 32ms. A test checks the incremental state matches a fresh read after every kind of write, and was checked to fail on a reuse bug.
