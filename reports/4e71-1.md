## How it was built

### Design notes

New file internal/mull/overlap.go holds it all. readOverlaps(s, g) walks the items in ID order, keeps those in flight (active, or in review and not SeenInGit), finds each one's work branches, lists the files each branch changed, and intersects every pair's sorted lists; the result goes in gitState.overlaps. It's a separate step from readGit, called only by Board, Overview and PlanPage, so item and phase pages and the tree pay nothing. readGit now keeps the branch heads it already reads (gitState.heads), so finding branch tips costs no extra call.

Work branches: the claim's branch when it's a work branch (a local branch that isn't a target, the release branch or mull), plus any other unmerged branch named <id>-… from ig.Branches. The claim's branch alone isn't enough: an item started on main (as in tests, and sometimes in practice) would otherwise diff the whole target, and an item that moved to a second id-branch would be missed. An item with no readable branch is skipped.

What a branch changed: the item note says claim base to branch tip, and I kept the claim base but made the start point smarter (decision c2e6). From the claim base alone, a worker who rebases onto, or merges in, the target would count everything that came in from it, giving false overlaps with whatever else touched those files. So it's measured from the merge base with the target's tip, unless the claim base is later than that or isn't on the target: work started on another item's branch (stacked) is then measured from where it started, so it doesn't overlap with the branch it's stacked on. Renames list both paths (--no-renames), since renaming a file another branch edits collides too. branchFiles is cached in a new LRU keyed by the three commit IDs (claim base, target tip, branch tip), as the answer never changes; up to three git calls per in-flight item when something moved (merge-base, merge-base --is-ancestor via the existing isAncestor, diff --name-only), none otherwise. knownCommit checks the claim base only after a branch is found, so items with no branch (the bench seed's) cost nothing.

Problems: overlapProblem puts the pair on the plan's side (the first in ID order when both are in it), so a cross-plan pair shows in both plans' blocks, naming the other item, its state, and up to five files with 'and N more'. Problem gains with and files (omitempty) so a supervisor reading JSON gets the full list.

Serve had no problems section, so I put the overlap where the human already looks at work in flight: an Overlap row after Agents in the Plans column, and a conditional Overlap field in the plan sheet's title block. Ink and muted text only, per the One Mark, One Job rule (an overlap isn't blocking, needs-you, now or done), and never clouded since it isn't a record. IDs get copy-ID buttons as every ID does. Rejected: a new Problems section in serve (bigger design change than this item, and serve shows no other problems yet), and clouding overlaps by item changes (arbitrary).
