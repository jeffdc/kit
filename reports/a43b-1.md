## What was built

### Summary

Jeff can reorder from mull serve: each open row of a ranked table (a phase's Items, a plan's Not in a phase, Unplanned) has up and down arrows beside its position, showing on hover or focus. A move saves on its first click as Jeff, sending the group's whole new order as a rank op, which the ops endpoint now takes; Jeff's move isn't clouded, and mull ready shows the new order. Focus returns to the moved item's arrow after the save, so the keyboard can keep moving it. DESIGN.md and mull guide json say so. Built on fbad (branch a43b-serve-reorder starts from fbad-serve-rank-order), so merge fbad first.

### UI tour

1. Open a phase with several open items and hover a row in its Items table.
2. Up and down arrows appear beside the row's number (the first row has no up, the last no down).
3. Click the down arrow: the row moves one place, the numbers update, and the toast says Moved <id> down: it's N of M now. The moved rows aren't clouded.
4. Tab to an arrow and press Enter (or Space) a few times: the item keeps moving, with focus staying on its arrow.
5. Run mull ready in a terminal: the phase's items come in the new order.
6. Unplanned and a plan's Not in a phase have the same arrows.

## How it was built

### Design notes

Server: rank joins uiOps in internal/serve/ops.go, so the page's POST …/ops runs it like mull batch's rank line (group and ids), as Jeff, under the commit check. The CLI's strictness (decision ed34) carries over: the page always sends every open item in the group, and a partial list is refused as batch_invalid (TestOpsRank checks both, plus that the two items whose rank changed are acknowledged, so Jeff's own move isn't clouded).

UI: rankTable in lists.js wraps itemTable for a group's table (phase ID, plan slug, or none). Its first column is the position plus the moves: for each open row, up and down moveButtons whose ops carry the whole open order with that item moved one place. The order comes from the rows as drawn, which are the group's open work in rank order (fbad), so unranked open items move too and the first move ranks them all. moveButton (write.js) is a 20px write with an arrow glyph and aria-label, data-now so write() saves at once. Each arrow has its own key (move:<pid>:<id>:<dir>), so state, failure and focus follow the item; rankTable disables the table's moves while any is pending, and lists any failure under the table.

Focus: save() in app.js now puts focus back on the button with the write's key after the post-save render, if focus fell to the body (a pending button is disabled). For a move that's the item's same arrow, now in its new row. Every write gets this; for writes whose button goes away it does nothing.

Rejected: drag and drop and move-to-first (Jeff chose up and down), arming moves (decided: one click), and arrows in the sheet index or What's next (the tables are where order is read). Checked in the dev server through headless Chromium over the DevTools protocol: on the demo's Launch phase, Move f86b up took it from 2 to 1 and Move 4012 down from 2 to 3, the toast said so, focus stayed on Move 4012 down, the arrows showed only on the focused row, and the moved rows weren't clouded. go test ./... passes.
