## How it was built

### Design notes

Docs are their own files, not the record body. A plan's doc is docs/plans/<slug>.md and a phase's is docs/epics/<id>.md: "docs/" plus the record's path (model.PlanDocPath, PhaseDocPath), plain markdown with no frontmatter. The record and its doc never share a write: putPlan/putPhase don't write the doc, and state.putDoc writes only the doc file (ending in one newline, deleting it when empty, writing nothing when unchanged). So the history of a doc file is exactly the doc's versions, which is what makes --log trivial and keeps the doc's diffs free of frontmatter churn. Mirroring the record path keeps one rule for 488d: when it moves epics/ to phases/ it moves docs/epics/ with it.

Loading: load() reads each plan's and phase's doc into a new Doc field (yaml:"-", json "doc,omitempty") beside Summary, so every place that prints a Plan or Phase (plan show, plan list, phase list, show, set) carries it with no extra code. Orphan doc files (no record) are ignored. Context gains item.phase_doc next to phase_summary; the plans brief stays compact.

Writes: two ops, "plan doc" {slug, doc} and "phase doc" {id, doc}, with doc a *string so a batch line that leaves it out fails (invalid_argument) instead of clearing a doc; "" removes it. Results are DocResult {type, id, doc}, and the op's id is the slug/phase ID, so @refs work (plan new -> plan doc -> plan agree in one batch). No state check: a shaping plan's doc must be writable, and set has none either. Writing a doc doesn't bump the record's updated.

CLI: docCmd builds both "plan doc <slug> [-]" and "phase doc <id> [-]" from three closures (read, history, op input). The optional argument must be "-" (stdin, via a.text); anything else is a usage error. --text prints raw markdown; --log prints {type, id, versions: [{commit, at, doc}]}.

History: store.History(path) runs git log --format='%H %ct' --no-renames on the mull branch's commit for that path, then one cat-file --batch over <commit>:<path> to get each version's content ("missing" means the commit removed it). It lives in store because store owns refs/heads/mull. Times are formatted RFC 3339 UTC like everything else. Each version carries its full text so a reader (the server, 482f) can diff; mull doesn't render diffs.

Sync: ValidDataPath allows ^(docs/)?plans/<slug>.md and ^docs/epics/<4hex>.md only; the test covers near misses (docs/items, docs/inbox, nested docs/docs, bad slugs).

summary is untouched and separate; 488d converts summaries into doc stubs with state.putDoc (write the summary as the doc when there is none) and decides then whether summary stays as a one-liner.

Rejected: making the doc the record body (summary renamed) — the doc's history would mix with every title/state change and 488d's migration would rewrite them all; a --diff flag — full versions are enough for any reader to diff.

Tests: internal/mull/docs_test.go (shaping plan doc, file layout, record untouched, unchanged write is no commit, phase list/show/context, --log versions incl. removal, not_found, batch with refs and required doc, sync pushes a doc); cmd/cmd_test.go TestDocCommands (stdin, --text, usage errors); shapes_test covers the new outputs and the doc key on plans and phases.

### Decisions made in the session

Accepting the review ratifies these. To decide one differently, before accepting: `mull decide <id> "..."`

- **9437** A doc is its own plain-markdown file on the mull branch, beside the record: docs/plans/<slug>.md for a plan and docs/epics/<id>.md for a phase (docs/ plus the record's path), with no frontmatter
  Why: Separate files keep a doc's history (its versions and diffs) free of the record's frontmatter churn, as the note's allow-list hint suggests; mirroring the record path lets mull migrate (488d) rename docs/epics along with epics/ in the same step
- **6280** summary stays as it is (the record's body); the doc is a separate field, and neither falls back to the other
  Why: Keeps this item additive. 488d turns summaries into doc stubs by writing each plan's (and phase's) summary to its doc when it has none, through the same state.putDoc, and then decides whether summary stays as a one-liner
- **00c9** plan doc / phase doc take only - as the optional argument (anything else is a usage error); the doc is replaced whole, and an empty doc removes the file. Batch ops plan doc {slug, doc} and phase doc {id, doc} with doc required
  Why: Matches the note's [-]: a doc is long text, so it comes only from stdin; a full replace keeps the op simple and diffs come from the versions. The batch field doc is required so leaving it out can't clear a doc
- **63c3** doc is an optional field on the Plan and Phase records, so it shows in plan show, plan list, phase list, show and set results; context gains item.phase_doc only (no plan doc, none in the plans brief)
  Why: One field everywhere the record prints is simplest for the UI and matches summary. The context briefing stays compact: the item's phase doc is what bears on the session; the plan doc is one command away (mull plan doc <slug>)
- **8e6e** Writing a doc does not bump the plan's or phase's updated time (the record file is not rewritten), and an unchanged doc writes nothing
  Why: Keeps a doc write a one-file commit and the doc's history clean; the doc's last change time is its newest --log version. If the UI's changed-since-you-looked wants updated bumped, that is a one-line change
- **cfbf** History is a --log flag on plan doc / phase doc: {type, id, versions: [{commit, at, doc}]}, newest first, one per commit that changed the doc file (doc empty where it was removed), read by a new store.History(path)
  Why: History from the commits is the point of the separate file: the UI (482f) and agents need versions without reading the mull branch themselves, so a small read is worth it. Each version carries its full text so diffs can be made by the reader; no diff output in mull
- **f3d3** A doc can be written in any plan state (shaping, active, done), with no --on-request
  Why: A shaping plan is a doc and questions, so its doc must be writable; set title/summary has no state check either, and fixing a done plan's doc is harmless. Like other plan and phase changes, agents write docs only when the human asks (protocol, not enforced)
