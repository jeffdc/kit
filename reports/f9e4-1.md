## How it was built

### Design notes

Two gaps, one item: view's problems in mull serve, and a phase's integration review packet.

**Problems.** `board()` in view.go computed each problem inline while it built the in-flight list. That logic moved, unchanged in output, into `state.itemProblems(item, itemGit, now)` (every kind but overlap) plus a small `unclaimedWork` predicate the board still uses for its in-flight rows; `mull view` prints exactly what it did (TestBoardFromGit still checks PROBLEMS (4)). pages.go wraps each problem in a `ProblemRow` (the Problem plus the item's title, stage, plan and phase with their titles) and gives the overview every plan-not-done's and unplanned work's (plan by plan in the Plans column's order, then unplanned, each in work order: the board's scope, so the two never disagree), the plan page its own, and the item page its own. All three pages already read git (`readGit`), so this adds no git calls: the inputs (`afterAccept`, `SeenInGit`, last activity) are all in the gitState they already build.

In the UI, a new `problems.js` draws a Problems schedule (ID, item with where it sits, stage, kind label over the text) between the overview's notes and its revision schedule, so it's the first thing on the sheet when something's wrong; the same on a plan's Status tab above the phase table; and on an item's sheet each problem as an ink `.note` with what usually fixes it. Ink and grey only and never clouded, as the overlap is (DESIGN.md's One Mark, One Job Rule: a problem needs a look, not an answer, so it's not in Needs you and takes no hue). Overlaps stay in the Plans column and the plan's title block rather than being listed twice. I considered putting problems into the Plans column's per-plan definition lists, next to Overlap: rejected, as that column is narrow and secondary, and done-but-unmerged work was the point of the plan.

**Integration review packet.** The item packet's builder became `state.packet(id, plan, reviews)`, used by `review(item)` and by `PhasePage`, which gains `reports` and `review`. Reports are found under `reports/<id>-` and matched on `item` or `phase`; the review entry is the newest `review` kind the filter picks (an item's by `item`, a phase's by `phase`), dropped when it's of an older report, as before. `Review` gains `target` (from `targetOf`, no git), so the phase's tour line can name the branch; the phase page still makes one git call.

In the UI, the packet moved out of item.js into `review.js` (`reviewPacket(pid, page, {it} | {phase})`), so both sheets share one component rather than a copy. For a phase: the title is "Integration review: does the phase hold together?", Accept writes `accept` on the review entry (the phase completes; the armed note says the phases that need it can start), Send it back writes `do` on the entry with the reason (mull adds the fix-up item; the settled header links it). "Items it covers" lists the report's items with their stage now (from the page's items) where an item packet has decisions, and the files are the "Combined diff by layer" with a line naming target, base and commit. The packet sits after Items and Needs you and before the doc, mirroring the item sheet, and the awaiting-review line links down to it. Both ops were already in `uiOps`, and as the human's own writes they pass the "filed from this worktree" guard; TestOpsIntegrationReview covers send back, the fix-up, and accept through POST …/ops.

**Demo.** dev-demo.sh's Design pass header now changes a file (so the combined diff shows) and its review has a tour with paths; "Fix the login redirect" gets an unclaimed commit, so the overview shows two problems (that and the favicon's "not on main"). The demo only seeds a fresh repo: `make dev-reset` to see it.

**Docs.** design.md (Problems row, Done on a phase), DESIGN.md (a Problems component, the phase packet, the overview layout, copy-ID list), `mull guide json` (overview/plan/item `problems`, ProblemRow, phase `reports`/`review`, Review `target`), and the supervisor guide (accept or send back on the phase's sheet).
