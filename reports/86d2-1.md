## What was built

### Summary

mull add "…" --follow-up <done-id> creates committed work in the done item's plan and phase, ranked last in its group, with from set to the done item; the done item is never reopened. It refuses an item that isn't done (invalid_state, pointing an in-review item at mull do) and a --plan or --phase that disagrees. accept --follow-up now builds its item the same way, so it records from too. The batch add op takes follow-up. mull view gains a work-after-accept problem: commits carrying a done item's Mull: trailer, on any local branch, authored after its latest accepted review; it shows while the latest is under a week old and clears once a follow-up of the item is added. design.md, mull guide json, the agents and supervisor guides, and kit's AGENTS.md describe both.

## How it was built

### Design notes

Follow-up item. NewItem gained a FollowUp field, resolved first thing in addItem by state.followUp: it loads the source item, requires it to be done, checks any given plan/phase agree (mirroring how add already refuses a --plan that disagrees with --phase), then fills Plan (NoPlan for unplanned work), Phase and From. Everything after that is the ordinary add path, so ranking (last in the group, or --before/--after), agreed-plan checks and batch refs all come for free. AddIn carries follow-up as a JSON field and ref field, and the CLI is one flag. accept --follow-up used to copy plan and phase by hand; it now passes FollowUp, which gives it from as well, and since acceptItem has already marked the item done the state check passes. I rejected a separate command for follow-ups: it is an add with a different source for its scope, and keeping it on add keeps one way to create committed work.

The problem. readGit already walks integration history and every other local branch's unmerged commits once. I added the author date (%aI) to the one log format and, during those same walks, count trailer commits whose author date is after the item's acceptance. acceptedAt computes that once per readGit: the latest accept settlement of a review entry for each done item, falling back to the item's updated time (never earlier than done, so the fallback can only under-report). Only trailers count, not id-branch membership or merge subjects, because merging the item's branch after acceptance is the normal flow and isn't new work. Author date rather than committer date so a rebase or cherry-pick of pre-acceptance commits isn't flagged. A commit seen on several branches is counted once (keyed by sha and item). The counts are unexported fields on ItemGit, so the item page's JSON shape doesn't change. There are no extra calls out to the repository, so the bench's call counts are unchanged and I didn't run make bench.

Clearing. The commits keep their trailer forever, so a permanent problem would be noise. It shows only while the latest such commit is within the existing recentActivity window (a week), and a follow-up item (from = the done item) created at or after that commit clears it at once; that is the remedy the problem's text names (mull add --follow-up <id>).

Tests: internal/mull/followup_test.go covers placement, rank, refusals, unplanned work, batch, accept --follow-up's from, and the problem (before vs after acceptance, main and a side branch, a backdated author date, clearing by follow-up and by age, the view text). cmd_test checks the flag is wired.
