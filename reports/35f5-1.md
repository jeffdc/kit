## What was built

### Summary

mull serve now pushes live updates. A Watcher (fsnotify) watches each registered repo refs/heads and git common dir (packed-refs, shared by every worktree) and the registry directory, debounces bursts for 150ms, and announces a project only when its mull branch tip moved, or when it was added to or removed from the registry while serve runs. GET /api/events is a text/event-stream with one project event per changed project ({id}), keepalive comments, and a clean end on shutdown. The placeholder page refetches on events and after a reconnect. New dependency fsnotify v1.9.0.

### UI tour

1. make build, then ./mull serve in one terminal (or --port 6899). 2. Open http://localhost:6855/ and, in another terminal, run any mull write in a registered repo (e.g. mull idea test in a scratch repo after mull init): the row updates within a fraction of a second, without reloading. 3. curl -N http://localhost:6855/api/events shows the opening comment, then event: project / data: {"id":"repo"} per write. mull init in a new repo announces the new project. A commit on main announces nothing. 4. Ctrl-C mull serve: it exits at once and curl ends. 5. go test -race ./internal/serve/

## How it was built

### Design notes

How: one Watcher (internal/serve/watch.go) owns an fsnotify watcher and a run loop; the SSE side (internal/serve/events.go) is the same type's ServeHTTP plus a small subscriber set.

- What is watched. For each registered repo: its git common dir (for packed-refs) and the ref's own directory, refs/heads (derived from store.Ref, not hard-coded), plus reftable/ when the repo uses the reftable backend. Directories, not files, because git replaces a ref by renaming a .lock over it. The common dir is shared by every linked worktree, so a write from any worktree is seen. The registry's directory is watched too (created if missing, as registry.Add would), so repos registered or removed while serve runs are picked up with no polling.
- Filtering and debounce. File events are filtered by name (mull, packed-refs, their .lock files, anything in reftable/) and gathered for 150ms from the first event of a burst, not reset on each event, so a steady stream of writes still refreshes. When the burst fires, each touched repo's mull branch tip is read (git rev-parse) and the project is announced only if the tip moved. That one check makes the name filter safe to be generous: lock files, failed compare-and-swaps, commits on other branches and pack-refs that change nothing produce no event. An fsnotify error (overflow) marks everything dirty and rereads.
- Registry changes. The registry is reread; projects added, removed or whose ID shifted (projectIDs renumbers when an earlier duplicate goes) are announced under old and new IDs, and watches are added or removed to match. A repo that can't be watched yet is retried on the next registry change (idea 4255 for surfacing that).
- Fan-out. Each open stream is a subscriber with a pending set and a one-slot wake channel. publish adds the ID and pokes the channel without blocking, so a slow client never blocks the watcher and never loses a project; repeats collapse. The stream writes "event: project" / "data: {\"id\"}" per pending project, sorted, and a ": keepalive" comment every 25s when idle. It ends when the client goes (request context) or the Watcher closes (wake channel closed).
- Lifecycle. cmd/serve.go starts the Watcher before printing its listening line, defers Close, and registers Close with srv.RegisterOnShutdown: http.Server.Shutdown waits for active handlers without cancelling them, so open streams would otherwise hold shutdown for its full 5s. A stream opened after Close gets 503.
- Handler. Handler(repos, opts ...Option): an Option adds endpoints to the mux; WithEvents(w) adds GET /api/events. Variadic so every existing Handler(repos) call, including the parallel workers', still compiles; the change in Handler is the signature plus a 3-line loop after the /api/projects route. Without the option /api/events is 404. No resolve.go was needed (events name IDs, they never look one up).
- Page. app.js opens an EventSource, refetches /api/projects on each project event (one fetch queued at most behind the current one), and refetches when the stream reopens after a drop, since events aren't replayed. It also now hides the table / shows status correctly when the list empties or a refetch fails, states only reachable with live updates.
- Tests (internal/serve/watch_test.go) use gittest temp repos and real mull writes (CaptureItem) from the main and a linked worktree, pack-refs then a delete that touches only packed-refs, registry add and hand edit while running, an end-to-end HTTP stream, keepalive with a 10ms interval, close ending streams, a cancelled client. They only wait for things to happen (10s bound) and never sleep to prove something didn't; "only when the tip moves" and the name filter are tested by driving mark/flush by hand on a Watcher with no run loop. Ran -race -count=15 clean.
- Dependency: github.com/fsnotify/fsnotify v1.9.0 (pulls golang.org/x/sys v0.38.0), decision b0ac. On macOS kqueue holds an fd per file in each watched directory (a few dozen per repo); Go raises the soft fd limit to the hard limit at startup, so this is fine for tens of repos.

### Decisions made in the session

- **b0ac** New dependency github.com/fsnotify/fsnotify v1.9.0 (with golang.org/x/sys) for the live-update watch
  Why: The item names it. It is the standard Go file watcher (kqueue on macOS, inotify on Linux), and polling each repo ref would cost a git call per repo per tick
- **2c2b** The watch is on directories, never files: each repo git common dir (packed-refs) and the ref directory (refs/heads), plus reftable/ if the repo uses the reftable backend. Events are filtered by name (mull, packed-refs and their .lock files)
  Why: A ref is replaced by renaming a .lock file over it, which a watch on the file loses. The common dir is shared by every worktree, so writes from any of them are seen
- **dec0** A burst of file events is gathered for 150ms from its first event, then each touched repo mull branch is read again, and a project is announced only if its tip moved
  Why: One mull write is a few events within milliseconds. Timing from the first event (not resetting on each) means a steady stream of writes still refreshes. Reading the tip filters out lock files, failed compare-and-swaps and pack-refs that change nothing
- **74e4** GET /api/events is text/event-stream: an opening comment, then event: project with data {id} per changed project, keepalive comments every 25s when idle, no replay. Repeats of a project pending for a slow client collapse into one event
  Why: The page refetches by project ID (projectIDs, as in /api/projects). JSON data leaves room for more fields. Collapsing per client means a slow page never blocks the watcher nor misses a project
- **e0f0** Repos registered or removed while serve runs are picked up by watching the registry directory (created if missing) and rereading it when the repos file changes. Added, removed or renumbered projects are announced under their old and new IDs
  Why: No polling, and the page learns of a new project at once. The directory is watched because the file may not exist yet or may be replaced by an editor. Creating the mull config dir is what registry.Add does anyway
- **4c5e** Handler takes variadic options, Handler(repos, opts ...Option), each adding endpoints to the mux. WithEvents(watcher) adds GET /api/events, which is 404 without it
  Why: Every existing Handler(repos) call keeps compiling, including those of the parallel workers. The watcher lifecycle stays with the command
- **1d69** mull serve starts the watcher before printing its listening line and closes it on shutdown through RegisterOnShutdown, which ends open event streams. A stream opened after that gets 503
  Why: http.Server.Shutdown waits for active handlers without cancelling them, so an open event stream would hold shutdown for its whole timeout
- **39fe** The placeholder page opens an EventSource on /api/events and refetches /api/projects on each project event (at most one fetch queued behind the current one), and once more when the stream reopens after a drop
  Why: A minimal live page until the UI lands. Events sent while disconnected are not replayed, so a reconnect refetches
