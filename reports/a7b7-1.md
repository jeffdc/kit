## What was built

### Summary

Opening a row in mull serve's sheet index no longer scrolls the index back to the top. reveal(), which keeps the current row in view, measured the row with offsetTop; a row with unseen changes sits in a cloud (.tcl.cl, position: relative), so its offsetTop was from the cloud and read as near the top. It now measures from the row's and the tree's boxes plus the tree's scroll.

### UI tour

1. Scroll the sheet index down to a row inside a red cloud (unseen changes) and click it.
2. The item opens on the right, and the index stays where it was, with the row highlighted.
3. Navigate to a clouded row that's out of view (for example from a link on the page): the index scrolls just enough to centre it.

### Checks (run by mull)

- `make done-checks`: pass, 20.0s

## How it was built

### Design notes

Cause: reveal() in tree.js computed the row's position as c.offsetTop - el.offsetTop. offsetTop is measured from the offsetParent, the nearest positioned ancestor. For an ordinary row that's .rail (sticky), so the subtraction worked. A clouded row sits inside .tcl.cl, and .cl is position: relative for its ::before outline, so its offsetTop was from the cloud: a few pixels. reveal took that as above the visible area and set scrollTop to it minus half the height, which clamps to 0. That's the jump to the top on every hashchange to a clouded row, and it also meant a clouded row out of view was never revealed.

Fix: top = c.getBoundingClientRect().top - el.getBoundingClientRect().top + el.scrollTop, the row's position in the tree's scroll content whatever its ancestors are. The rest of reveal is unchanged. I rejected making .tcl unpositioned, since the cloud's ::before needs it.

Checked in headless Chromium with a copy of both versions of reveal on a tree with a positioned cloud: with the clouded row visible at scroll 1100, the old version went to 0 and the new one stays at 1100; from scroll 0, the old one stays at 0 (never reveals) and the new one scrolls to 1075. I also confirmed offsetTop isn't affected by the tree's own scroll, so ordinary rows were never wrong.
