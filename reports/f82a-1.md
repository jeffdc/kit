## What was built

### Summary

Plans, and optionally phases, now take rules: Jeff's standing rules for the agents working in them, plain markdown kept like a doc at rules/plans/<slug>.md and rules/phases/<id>.md. mull plan rules / mull phase rules [-] [--log] [--text] read and write them (and batch has plan rules / phase rules ops); mull context --item gives the item's plan_rules then phase_rules in full, with a protocol line to follow them when there are any. mull serve shows and edits them under the doc, and the change feed reports plan_rules and phase_rules changes. design.md, json.md, the agents guide (and kit's AGENTS.md copy) and serve's DESIGN.md are updated; the supervisor guide is left to cc99.

### UI tour

1. Run make dev and open http://localhost:6899/#/demo, then open any active plan.
2. In the plan's title block, see a new Rules field reading none.
3. Open the Plan doc tab: under the plan doc there's a section The rules saying No rules for this plan, with a Write the rules button.
4. Click Write the rules, type a couple of markdown bullets (mention a phase ID such as one from the Status tab), and save: the rules render under the doc, the ID becomes a status link with a margin row, and the button now says Edit the rules.
5. Open one of the plan's phases: after The phase doc there's The rules, saying No rules for this phase. Its workers follow the plan's. Write some and save.
6. In a terminal in the demo repo, run mull context --item <an item in that phase>: item.plan_rules and item.phase_rules hold the text in full, and protocol ends with the line to follow them.
7. From the terminal run mull plan rules <slug> - with new text on stdin, then reload: the Plan doc tab, the Rules field (changed since …) and the rules heading are clouded, and the project's revision list shows <plan>: plan rules, rules edited.

## How it was built

### Design notes

Rules are built as a second doc beside each plan's and phase's doc, reusing the doc machinery rather than adding a new kind of record.

Storage: rules/ plus the record's path (rules/plans/<slug>.md, rules/phases/<id>.md), each its own plain-markdown file, written with the same putDoc/getDoc helpers, so writing rules never touches the record or the doc and their history is only their own. model gains PlanRulesPath/PhaseRulesPath and two dataPaths patterns, so sync pushes them and still refuses anything else. I rejected docs/plans/<slug>.rules.md: the loader's baseName and the docs/plans/ pattern would have had to tell the two apart, and rules/ mirrors docs/ exactly. Only format 2 has rules (writes are refused on format 1), so there's no legacy path. Plan and Phase gain a Rules field (yaml "-", json rules,omitempty) loaded beside Doc; the read-only state cache's blob check now includes the rules path. Phase delete removes the rules file with the doc.

Operations: internal/mull/docs.go gets PlanRules/PhaseRules, SetPlanRules/SetPhaseRules and the --log readers, which reuse docLog and only rename doc to rules in the output. Batch has "plan rules" and "phase rules" ops with a required rules pointer (as doc is required), so leaving the field out can't clear them. No --on-request: docs have none either, and rules are Jeff's in the same way (the protocol says not to change them unasked).

CLI: the old docCmd became a generic textCmd (print, - to replace from stdin, --log, --text) that docCmd and the new rulesCmd wrap, so plan/phase doc behave exactly as before and plan/phase rules behave the same way.

Context: ContextItem gains plan_rules and phase_rules, given in full. The protocol gets one more line ("Follow the item's plan_rules, then its phase_rules…", with the human's name) only when the item has either, so sessions without rules, or without an item, see no change. The "don't change plans, phases or their docs" line now says "docs or rules".

Change feed: plan_rules and phase_rules are record types of their own, like plan_doc and phase_doc (diffRecords, changePaths, ordering), so serve's clouds, acknowledgement after a page write and the stale-write conflict check all cover rules with no extra code.

Serve: a small rules.js renders a "The rules" section (renderDoc, so IDs link with the status margin; doc_refs now cover the doc and the rules) with an editWrite on field "rules", placed under the plan doc on the Plan doc tab and after the phase doc on a phase's sheet. The plan's title block gets a Rules field (none / changed since / no changes since), and the Plan doc tab clouds when either the doc or the rules changed. The serve op allowlist takes plan rules and phase rules. The revision schedule labels these changes "<title>: plan rules" and "rules written/edited".

Docs: design.md (records table, storage layout, a Rules paragraph, command table, context description, protocol outline), json.md (records, command shapes, batch ops, context, change types, serve pages and allowed ops), agents.md and kit's AGENTS.md copy (follow plan_rules then phase_rules; read with plan/phase rules), and serve's DESIGN.md. The supervisor guide is left to item cc99.

Tests: rules round trip, file paths and single-file commits, no-op rewrite, context fields and the conditional protocol line, history, not-found errors, batch and sync (TestPlanAndPhaseRules, TestRulesInBatchAndSync); data paths; phase delete removes rules; the revision feed reports plan_rules and phase_rules; serve writes both from the page and acknowledges them; CLI rules commands end to end (TestRulesCommands).
