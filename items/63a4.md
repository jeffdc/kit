## The problem: backlog items can't just be worked

Seen in kit and oaks (2026-11-21 to 23):
- `mull start <capture>` commits it into the phase it's tagged to. If that phase was complete, it reopens, and phases that need it are blocked again.
- One item can't close several captures. Agents add a new item, write "Covers bug 65c2" in its notes, and drop the captures. Examples: oaks 1adb, 7cac and c49c replaced 10df, a590, 65c2 and 5039; c13c absorbed f0e0. kit a412 replaced 4f9f; eda9 replaced d1c5; da55 and f9e4 absorbed 60c3, 50aa, dc0f and a58b.
- The dropped captures read as "not worth doing". The only link to the work that fixed them is prose.
- A duplicate has no outcome but drop (075b, dropped for 50c4).

## Proposal (to work through)

- **Start never touches a phase.** A capture started from the backlog is plan-level work. It's in a phase only when committed there on purpose (`mull commit --phase`). Its tag is kept as "about phase X".
- **One item can cover captures.** `mull start <id> --covers <c1> <c2>`, or `mull set <item> covers …`, sets `covered_by` on each capture:
  - covered captures leave the backlog and show under the item;
  - when the item is accepted, they're done, recorded as covered by it;
  - when the item is dropped, they return to the backlog;
  - the report lists them.
- **Duplicates:** cover one capture with the other. Drop means only "not worth doing".
- **Guides:** never re-add a capture as a new item. Start it, or cover it.
- **Cost:** one field (`covered_by`), one rule change in start and commit, and guide text. No new stage.

Open questions:
- Should a started capture keep "about phase X", or become plain plan-level work?
- Should covers apply only to captures, or also let one committed item cover another?

## Other holes in the overall workflow

1. **Protocol line has the wrong order.** context's protocol says "mull start <id>; branch <id>-<name>". Started in that order, the claim records the wrong branch (it happened to 813e and f82a). It should say branch first, then start. The plan rule says so; the protocol doesn't.
2. **Merge churn.** 7 of 18 item merges conflicted, mostly in view.go, links.go, design.md and json.md. Each one went back to its worker to merge main. The overlap problem only shows a collision after work has started. Nothing warns at hand-out, and nothing helps the supervisor schedule around hot files.
3. **Review load.** Most items carried 3–9 decisions for Jeff, many of them trivia ("updated AGENTS.md too", "no json change"). The decision filter needs a bar: file only choices Jeff would care about.
4. **AGENTS.md drift.** Every guide change is copied into kit's AGENTS.md by hand. AGENTS.md should point at `mull guide agents` (or be generated from it), not duplicate it.
5. **Installed binary lags the build.** Workers run the installed mull, so new commands and rules reach them only after `make install`, which restarts serve. No version check tells an agent it's on an old mull.
6. **UI is untested before review.** Workers may not run servers, so serve changes reach Jeff checked only by node syntax or render stubs. Walking a tour needs `make dev-reset`, which wipes and reseeds the demo and needs Jeff's OK each time.
7. **Scratch leaks.** Workers shared one scratchpad and overwrote each other's builds. Scratch demo repos got registered with mull serve, so 2 appear in Jeff's project list (bug e0b3: no way to unregister).
8. **Accept before merge.** Jeff accepted ed9d in serve before it was merged. The new problem catches it, but serve doesn't show the order: merge, then walk the tour, then accept.
9. **Ungated plan settings.** Agents can change a plan's target, preview, rules, doc and shared globs without `--on-request`. Only the guides stop them. Decide which of these the gate should cover, as was done for checks.
10. **Agent identity.** Decisions and entries record `by` as a worktree path (…/agent-a0bf31b5…). It means nothing once the worktree is removed.
11. **Harness branches.** The harness leaves worktree-agent-… branches. `mull worktrees` doesn't list them, and they had to be deleted by hand (part of da55).
12. **Cost of new reads.** Overview went from 36.6 to 47.1 ms in kit when it has worktrees (1499). Overlap reads are timed only with no real branches (idea f265).
