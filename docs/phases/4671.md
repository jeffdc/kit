The server learns to write, once, for every edit to come. Nothing visible changes in the UI yet.

- **Ops endpoint.** `POST /api/projects/{id}/ops` takes a list of ops in the shape `mull batch` reads (op name plus its fields) and runs them through the op registry in one commit, all or nothing. Only the ops the UI offers are allowed; anything else is refused. It sits behind `writeAllowed`, as Mark revision seen does.
- **Made by the human.** A write through the endpoint is recorded as the human's, by the repository's git user.name, not by a worktree and not as an agent's on request. Human-only ops (commit, triage, plan agree, promoting an idea…) take it as the human's own say. The server refuses writes when user.name isn't set.
- **Stale pages.** Each request carries the revision commit the page showed. If any record the ops touch changed after it, the server answers with a conflict and writes nothing.
- **Acting acknowledges.** The per-machine last look (seen.json) keeps, beside its commit, the records the human has acted on and the commit that acted. The revision API leaves out changes to an acknowledged record up to that commit, so neither the record's earlier changes nor the write itself is clouded; a later change by anyone else clouds it again. Mark revision seen clears the list.

Done when an ops request from the page writes one commit recorded as the human's, a stale one is refused, and what it touched is no longer clouded.
