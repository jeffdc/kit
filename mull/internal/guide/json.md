# mull output reference

Every command prints one JSON value to stdout. Most print an object; `batch` prints an array. `view`, `inbox`, `report`, `guide`, `migrate`, `plan doc`, `phase doc`, `plan rules` and `phase rules` also have `--text` for a human rendering. Treat the JSON as the contract: the text form may change.

`field?` means the field is left out when it's empty. A list that's always present is written `[]`.

## Errors

On failure, mull prints nothing to stdout, prints this to stderr, and exits 1:

```json
{"code": "not_found", "error": "no item \"ffff\""}
```

`code` is stable: branch on it, not on the message. Codes:

| code | meaning |
|---|---|
| `usage` | bad command line: unknown command or flag, wrong number of arguments |
| `invalid_argument` | a value is malformed or missing |
| `not_a_repo` | not inside a git working tree |
| `not_initialized` | no `mull` branch (run `mull init`, or `mull sync` on a second machine) |
| `already_initialized` | `mull init` where the branch exists |
| `not_found` | no such plan, phase, item, entry, report or guide |
| `already_exists` | a plan slug or batch ref already used |
| `invalid_state` | the record is in the wrong state (e.g. accepting an item that isn't done) |
| `claimed` | the item is claimed by another worktree |
| `already_settled` | the inbox entry is already settled |
| `not_allowed` | not allowed (kind rules; a worker accepting its own work; promoting an idea, creating a plan, agreeing one, changing the hard checks (`config checks`, `plan checks`), risk (`config risk`), setup (`config setup`), the map (`config map`, `map --record`), the parallel cap (`config set parallel`), growing a ratchet (`rules ratchet --grow`), migrating or recording the human's own decision (`decided --human`) without `--on-request`; a `mull serve` write with no `mull name` or git `user.name`, or of an op its pages don't offer; needs on an item, or a phase needing an item) |
| `dependency_cycle` | the needs would form a cycle |
| `scope_required` | say which plan or item: `--plan` or `--item` (or `--phase`, or `--plan none` for unplanned work, for `add`) |
| `rules_required` | `done` was given no `--rules` answer (`none`, or which rules the work touched and how) |
| `at_capacity` | as many items are active as config's `parallel` allows (3 by default) |
| `setup_failed` | a `config setup` command failed in the new worktree, which `start` removed again |
| `behind_target` | the item's branch lacks its target's tip: `git merge <target>`, then `done` again |
| `no_checks` | no hard checks configured |
| `dirty_tree` | uncommitted or untracked changes |
| `checks_failed` | the hard checks failed |
| `sync_conflict` | the same records changed here and on the remote |
| `push_refused` | the mull branch holds non-mull paths |
| `remote_error` | the remote couldn't be reached or refused the push |
| `batch_invalid` | one or more batch lines failed; nothing was written |
| `invalid_json` | a batch line isn't a JSON object |
| `busy` | too many concurrent writers; try again |
| `conflict` | a write from a `mull serve` page touches records that changed since the page showed them; nothing was written |
| `git_error` | git failed unexpectedly |
| `retired` | a retired command or batch op (`loose`, `ideas`), or a phase's integration review (retired: drop it); the message names its replacement |
| `migration_required` | a write to data from before Model v2 (format 1), or to data holding records still in format 1 (merged in by `sync` from an older mull): the human runs `mull migrate --dry-run`, then `mull migrate --on-request`. Reads still work |
| `unsupported_format` | the data is in a newer format than this mull understands: update mull. Reads fail too |
| `port_in_use` | `mull serve`'s port is taken, most likely by another `mull serve`: pass `--port` to use another |
| `launchd_error` | `mull serve --install` couldn't load the LaunchAgent: the message carries launchctl's output |
| `internal` | anything else |

A `batch_invalid` error also lists every failed line:

```json
{"code": "batch_invalid", "error": "2 of 40 batch lines failed; nothing was written",
 "lines": [{"line": 7, "op": "add", "ref": "webhook", "code": "not_found", "error": "no phase \"ffff\""}]}
```

## Records

- **Plan:** `{slug, title, state ("shaping"|"active"|"done"), created, updated, summary?, target?, preview?, doc?, rules?, checks?: [], shared?: []}`. A new plan is `shaping`; `plan agree` (the human) makes it `active`, and `plan close` makes it `done`. `target` is the branch its work lands on (`plan new` makes it `plan/<slug>` unless `--target` says otherwise; `plan set <slug> target <branch>`); absent, it lands on the integration branch (see Target). `preview` is the URL that serves the target (`plan set <slug> preview <url>`): mull records it and never runs or checks it. A shaping plan takes captures and inbox entries but refuses phases and committed items (`invalid_state`) until it is agreed. `checks` are the plan's own hard checks (`plan checks`): shell commands `done` runs for the plan's items after config's `done_checks`. `shared` are the globs for files its parallel work shares (`plan shared`): `done` flags an item's changes to them in its report.
- **Phase:** `{id, plan, title, needs?, from?, created, updated, summary?, doc?, rules?}`. `from` is the inbox entry (e.g. an idea) it was promoted from. `needs` are the phases it waits for: needs exist between phases only. (A need on an item, from before Model v2, still counts until `mull migrate` makes it a need on that item's phase.)
- **Docs:** `doc` is a plan's or phase's doc, in markdown: a plan's picture, done-when and why the order; a phase's design and done-when. Docs hold intent only, never status: status comes from the records. A doc is kept apart from its record, so changing the record (`summary` included) never makes a new version of the doc. `plan doc` and `phase doc` print it, replace it (`-`) and list its versions (`--log`).
- **Rules:** `rules` are a plan's or phase's standing rules for the agents working in it, in markdown: the human's, like docs (how to set up a worktree, what to use, what not to touch, skills to load). `context --item` gives an item's plan's rules, then its phase's, in full. They're kept apart from the record and the doc, each in its own file, and `plan rules` and `phase rules` print, replace (`-`) and list them (`--log`) as `plan doc` does a doc.
- **Item:** `{id, plan?, phase?, rank?, title, state ("captured"|"committed"|"active"|"in-review"|"done"|"dropped"), kind?, category?, area?, covered_by?, source?, needs?, docs?, claim?, from?, created, updated, notes?}`. `area` is where in the code it is (a path or glob); `covered_by` is the item whose work covered it (`done --covers`), done with it. `from` is the inbox entry (idea, question or loose end) it was made from, or the done item it follows up (`add --follow-up`, `accept --follow-up`). `rank` is its order in its group, lower first (see Rank).
  - **No `plan`** means unplanned work, or (captured) backlog not tagged to a plan.
  - **Captured items** (`mull bug`, `mull idea`) carry `kind` (`"bug"`|`"idea"`), and `category` and `source` when given; `notes` holds the `--detail`. They keep them once committed.
  - **Captured items are the queue**, the agents' own: anyone commits one (`commit`) or starts it. Starting one tagged to a complete phase makes it the plan's work, noting the phase, rather than reopening it.
  - **claim:** `{worktree, branch, at, base?}`
  - **Items have no needs.** An item's `needs`, from before Model v2, is kept and shown until `mull migrate` drops it, but no longer affects readiness.
- **Rank:** the order of open work (committed, active, in review) within its group: a phase, a plan's items with no phase, or Unplanned. It sorts and never affects readiness. Agents never write the numbers: `mull rank` sets a group's order, and mull writes ranks a step of 10 apart. Committed work joins its group last (`add`, `commit`, `start` of a captured item, `set <id> phase` to another group), or just `--before`/`--after` an open item in the group; when there's no gap there, the group's open work is renumbered in order. Captured items have no rank, and done and dropped items keep theirs. An item without a rank (from before ranks) sorts after ranked ones, oldest first, until its group is next ranked or joined. **Work order** is how `list`, `ready`, `context`, `view` (`in_flight`), `show` and `plan show` list items: plan by plan (by slug, Unplanned last); within a plan, its phases in schedule order (by depth of needs not yet done, then age; done phases last), then its items with no phase; within a group, open work in rank order, then the rest (captured, done, dropped) by rank, unranked last.
- **Target:** `{branch, from ("plan"|"integration"), found, ahead_of_release}`: where a plan's work lands, and where seen in git is measured (work on the release branch counts as landed too). `from` is `"plan"` when the plan sets its own `target` and `"integration"` when it falls back to the integration branch (as unplanned work always does): config's `integration`, unless that's the release branch, where mull never lands work; then the standing branch `next`. `found` is `false` when the branch doesn't exist; `ahead_of_release` counts its commits the release branch doesn't have (0 when it is the release branch).
- **ItemView:** Item plus `{ready, blocked_by?}`. Ready means committed, in a phase whose needs are done (or in no phase), in a plan that isn't shaping; `blocked_by` lists the phase's needs that aren't done.
- **PhaseView:** Phase plus `{progress, complete, blocked_by?}`. `complete` means every committed item is done or dropped (at least one).
- **Progress:** `{total, captured, committed, active, in_review, done, dropped, ready}`. `total` counts committed work (every stage but captured); captured items tagged to the phase or plan are counted only in `captured`.
- **Entry** (inbox): `{id, kind ("decision"|"question"|"review"|"loose-end"|"idea"), text, plan, item?, source?, by, created, settled?, decisions?, landed?, default?, due?, detail?}`. An agent's own decision (`decided`) is settled at once with action `note`: in its report and the decision log, never in the inbox. A question carries `default` (what the agent does if nobody answers) and `due` (when that default stands). A review with `landed` (`"medium"` or `"sampled"`) is a look at work that already landed: accepting says it looked fine, and sending it back (`do --reason`) files a follow-up item. `plan` is `""` for an entry about the whole project or an unplanned item.
  - **phase** and **items**: integration reviews of phases are retired; an old one is shown with them, and can only be dropped.
  - **settled:** `{action ("accept"|"decide"|"do"|"drop"|"park"|"note"), note?, item?, phase?, by, human?, on_request?, at}`. `item` or `phase` is what `do` made. `by` is the worktree that settled it; `human` is `true` when the human settled it themselves (from `mull serve`), and then `by` is their name (`mull name` on that machine, or else the repository's git `user.name`).
  - **decisions** (reviews only): the IDs of the decision entries the review carries: every unsettled, unparked decision on its item when `mull done` filed it. Accepting the review ratifies those still unsettled (settled note `with review <id>`). Decide one differently first with `decide <id>`; sending the review back leaves them open, and the next `done` carries them again.
  - **Loose ends and inbox ideas** (`kind: "loose-end"`, `"idea"`) are retired: captured items replaced them, and nothing files them any more. Existing ones are kept until `mull migrate` turns them into captured ideas: listed only by `inbox --kind loose-end|idea`, counted in the view's `legacy`, never in `needs_you`, and settled as before (an idea's `text` is its title and `detail` its note).
- **Report** (done report): `{item?, phase?, items?: [{id, title}], n, passed, override?, commit, base?, at, by, summary, tour?, checks (as `check` prints it, without `cached`), changes?: [{layer, files: [{status, path, added, removed}]}], shared?: [{status, path, glob}], design?, decisions?: [{id, text, detail?}], warnings?: [], rules?, slowed?, risk?, risk_why?: [], sampled?, rule_checks?: [{id, passed, exit?, count?, new?: [], fixed?, duration_ms, tail?}], in_scope?: [], covered?: [], nearby?: [], new_edges?: []}`. Since the redesign: `rules` is the agent's answer to whether the work touched a rule, `slowed` what slowed it, `risk` the band done scored (`low`, `medium`, `high`) with `risk_why` its reasons and `sampled` whether low-risk work was drawn for the human; `rule_checks` are the rulebook's checks as done ran them (`passed` is false if any failed), `in_scope` the rules whose scope the change touched, `covered` the items it covered, `nearby` the queued items in the area it changed, and `new_edges` the connections it added to the map. What was built (`summary`, `tour`, `checks`) and how (`design`, `decisions`, `changes`). `tour` is the steps as the agent wrote them, which name pages by path (`/trees/quercus-alba`); `warnings` are done's soft warnings, such as a tour step giving a full local URL (`http://localhost:4001/…`) whose scheme, host and port aren't the item's plan's preview. `design` is the design notes, present on every report since `done` required them; `decisions` are the decisions the review carries, as they were when `done` ran. `shared` lists the changed files (of `changes`, by path) that match the item's plan's `shared` globs when `done` ran, each with the first glob it matched; reports from before have none. An item's report has `item`. A phase's integration review report (`done <phase-id>`) has `phase` and `items` (its done items, in work order) instead, no `decisions` (its items' reviews carried theirs), `commit` the target's tip it was run on, and `changes` the phase's combined diff: the files its items' latest done reports changed, from `base` (the merge base of their claims' bases) to `commit`, so other work merged meanwhile on other files is left out.
- **Config:** `{format, integration, release, remote, done_checks: [], layers: {name: [globs]}, risk: {high: [globs], max_lines, max_files, sample}, worktrees?, setup?: [], parallel?, map: {edges?, allowed?}}`. `risk` is how done scores risk (unset fields take the defaults: the default high-risk paths, 400 lines, 15 files, 20 percent sampled); `worktrees` is where `start` makes worktrees (default a sibling of the main worktree, `<repo>.work`), `setup` the commands it runs in a new one, `parallel` how many items may be active at once (default 3), and `map` the commands that print the code's connections and the declared ones. `format` is the data's storage format: `2` (Model v2) once migrated, and in every repository `mull init` made since; `1` for data from before Model v2, which mull reads but won't write until `mull migrate`.

Times are RFC 3339 in UTC. IDs are 4 hex characters; plans use their slug.

## Commands

| command | prints |
|---|---|
| `init` | `{initialized, branch, config: Config}` |
| `version` | `{version}` |
| `name` | `{name, file}`: the name this machine's human goes by (`""` when unset) and the file it's kept in. `name <name>` sets it, and `name ""` clears it. It's per machine, never on the mull branch. |
| `plan new`, `plan agree`, `plan close` | Plan |
| `plan checks` | Plan. `plan checks <slug> [command...] --on-request` replaces the plan's own hard checks, each argument one shell command (trimmed; empty ones left out), and no commands removes them. Only the human changes them, since they judge agents' work: `not_allowed` without `--on-request`, as for `config checks` |
| `plan shared` | Plan. `plan shared <slug> [glob...]` replaces the plan's shared globs (trimmed; empty ones and repeats left out), matched as config layers' are, from the repository's root (a leading `/` or `./` is `invalid_argument`), and no globs removes them |
| `plan set` | As `set`, for a plan only (`not_found` for anything else): `<slug> title\|summary\|target\|preview <value>`. `target` takes a branch name (a leading `refs/heads/` is dropped; `""` clears it); one git refuses, or `mull`, fails with `invalid_argument`. The branch needn't exist yet. `preview` takes an absolute `http` or `https` URL with a host (trimmed; `""` clears it); anything else fails with `invalid_argument`. It's never fetched, so the server needn't be up |
| `plan list` | `{plans: [Plan + {progress}]}` |
| `plan show` | Plan + `{progress, phases: [PhaseView], items: [ItemView]}` |
| `phase add` | Phase |
| `phase delete` | `{phase, untagged, unneeded}`: `phase` is the deleted Phase as it was, `untagged` the captured items moved up to its plan and `unneeded` the phases whose need on it was removed. Only a phase with no committed work in any stage (committed, active, in review, done or dropped) can be deleted: otherwise `invalid_state`, naming the items. Only the human deletes a phase (`not_allowed` without `--on-request`). Its record, doc and rules are removed from the mull branch, whose history still has them |
| `phase list` | `{phases: [PhaseView]}` |
| `phase set` | As `set`, for a phase only (`not_found` for anything else): `<id> title\|summary\|integration-review <value>`. `integration-review` takes `on` or `off` (anything else is `invalid_argument`), and only the human changes it: `not_allowed` without `--on-request`, through `phase set` or `set`. Setting it to what it is writes nothing |
| `plan rules`, `phase rules` | `{type: "plan"\|"phase", id, rules}`, as `plan doc` and `phase doc` with `rules` for `doc`: `""` when there are none, `-` replaces them from stdin (empty removes them), `--text` prints them as markdown, and `--log` prints `{type, id, versions: [{commit, at, rules}]}` |
| `plan doc`, `phase doc` | `{type: "plan"\|"phase", id, doc}`: `id` is the plan's slug or the phase's ID, and `doc` is `""` when there is none. `<slug\|id> -` replaces the doc from stdin, and empty stdin removes it. `--text` prints the doc as markdown. `--log` prints `{type, id, versions: [{commit, at, doc}]}`, newest first: one version per commit that changed the doc, `doc` `""` where it was removed |
| `add`, `release`, `commit` | ItemView |
| `bug`, `idea` | ItemView + `{similar: [{id, title}]}`: the captured item, and up to five open captured or committed items (most similar first, `[]` when none) whose titles overlap its own a lot in their words, rarer words counting for more. A hint that it may be a near-duplicate, never a block: the capture is written either way |
| `show` | `{type: "plan"\|"phase"\|"item"\|"entry", <type>: …}`. A plan is shown as in `plan show`, a phase as PhaseView + `{items}`, an item as ItemView, an entry as Entry |
| `list`, `ready` | `{items: [ItemView]}`, in work order (see Rank). `list --plan none` selects items with no plan; `--kind bug\|idea` selects captured kinds |
| `set` | `{type: "plan"\|"phase"\|"item", plan?: Plan, phase?: PhaseView, item?: ItemView}`. Plan fields: `title`, `summary`, `target`, `preview` (see `plan set`). Phase fields: `title`, `summary`. Item fields: `title`, `notes`, `category`, `area`, `phase`, `doc`, `plan` (queued or committed work only: moving is a move, and a new plan leaves the old phase behind; `none` for unplanned), and for a captured item `kind` (`bug` or `idea`). An item set to a phase in another plan moves to that plan; moving active or finished work fails with `invalid_state` |
| `need`, `unneed` | `{type: "phase", phase: PhaseView}`. Only a phase has needs, and only on phases; on an item they fail with `not_allowed` |
| `rank` | `{plan?, phase?, items: [{id, title, state, rank}]}`: the group (neither for Unplanned) and its open work in the new order. `mull rank <phase\|plan\|none> <ids...>` names the group by phase ID, plan slug (its items with no phase) or `none` (Unplanned), and must list every open item in it, first to last: a missing one, or one that isn't open work in the group, fails with `invalid_argument` naming it |
| `start` | `{item: ItemView, warnings: [], worktree, branch, target, pruned?: []}`: start makes the item's branch (`<id>-<slug of its title>`) from its target, making the target from the release branch if it's missing, makes a worktree for it (in config's `worktrees`), runs config's `setup` there with `MULL_MAIN` and `MULL_ITEM` set, and claims the item for that worktree; `pruned` are merged worktrees it removed first. A target that is the release branch is `invalid_state`. `--here` claims it for this worktree on the branch checked out instead (the batch op `start` does too). More active items than `parallel` allows is `at_capacity`. Starting a blocked item is allowed with a warning, and so is starting committed work while open work ranked before it in its group isn't done: the warning names those items, with their stage. Equal ranks and unranked items have no order, so they don't warn, and nor does a captured item started now (it joins its group last, unranked by anyone). A captured item tagged to a shaping plan can't be started (`invalid_state`), since starting commits it |
| `decided`, `ask` | Entry. `decided --human --on-request` (the human's own decision) returns it already settled: `settled` is `{action: "decide", note: <the text>, by: <worktree>, on_request: true, at}`, so it's in `decisions` at once and never in `inbox`. `--on-request` without `--human` is `invalid_argument` |
| `inbox` | `{entries: [Entry]}`, oldest first: questions, decisions and reviews. Loose ends and ideas only with `--kind loose-end\|idea`. `--plan none` for entries with no plan |
| `loose`, `ideas` | retired: fail with code `retired` |
| `accept` | `{entries: [Entry], items: [ItemView], follow_up: ItemView\|null, warnings?: []}`. `entries` includes the decisions an accepted review carried and ratified. Accepted work lands on its target by fast-forward; `warnings` say when it couldn't. Accepting a look at landed work settles it and leaves the item as it is. `--follow-up` is for one reviewed item only |
| `decide`, `park` | Entry |
| `do` | `{entry: Entry, item?: ItemView, phase?: PhaseView}`: the new item (or phase, with `--as phase`), or the reopened item for a review. For a look at landed work, `item` is the follow-up it files, in the landed item's plan and phase, carrying the reason (required) |
| `drop` | `{entries: [Entry], items: [ItemView]}` |
| `decisions` | `{decisions: [{id, plan, item?, kind, context, decision, by, human?, on_request?, noted?, why?, at}]}`, newest first; `by` and `human` as in an entry's `settled`; `noted` marks an agent's own choice (with `why`), never put to the human |
| `config`, `config set\|checks\|layer` | Config |
| `view` | `{generated, integration, integration_found, release, ahead_of_release, plans: [Board], queue, clusters?: [{area, count, items}], unlinked_commits_this_week, unlinked_recent?, unplanned?: Board, legacy?: {loose_ends, ideas}, prunable_worktrees?: {count, bytes}, format, migration_required?}`. `prunable_worktrees` counts the claim worktrees `mull worktrees` marks prunable, and their size in bytes, across every plan (closed ones too; with `--plan`, that plan's only), present when there are any. `format` is the data's storage format (as in Config); `migration_required` is `true` while writes are refused until `mull migrate`. `unplanned` is a Board (slug `""`, title `"Unplanned"`, no `state`) for items with no plan and entries with no plan, present when there are any. `queue` counts the whole project's queued items (captured, not covered), with `--plan` too, and `clusters` are the areas holding three or more of them; each Board's `progress` counts its own. `legacy` counts open loose ends and inbox ideas until `mull migrate`. `plans` holds the active plans, then the shaping ones; a done plan only with `--plan`. Board: `{slug, title, state?, target: Target, preview?, progress, phases: [{id, title, progress, complete, blocked_by?}], unfiled: Progress, problems: [{kind, item, with?, files?, text}], in_flight: [{id, title, state, worktree?, branches?, commits, last_activity?}], needs_you: {reviews, decisions, questions, older_than_a_week, parked}}`. Problem kinds: `idle-claim`, `unclaimed-work`, `done-not-in-git` (nothing on its plan's target: in review for three days, or done (accepted) at once), `failed-done`, `work-after-accept` (commits carrying a done item's trailer, on any branch, written after it was accepted, merge commits aside: shown while the latest is under a week old and no follow-up of it has been added since), `overlap` (it and the item `with`, both in flight, changed the same `files` on their branches: see Overlap below; on the plan's side of the pair, or the first in ID order when both are in it). The top-level `integration`, `integration_found` and `ahead_of_release` are config's integration branch; each Board's `target` is its plan's (integration for `unplanned`), and `preview` its plan's preview URL |
| `context` | `{worktree, branch, protocol: [], item?: …, my_claims: [], plans: [], ready: [], active: [], rules: [Rule]}`. `rules` is the rulebook (see `rules`), in full; when there is one, `protocol` ends with a line saying to follow it. While writes wait for `mull migrate`, `protocol` starts with a line saying so. `plans` are the shaping and active plans: `{slug, title, state, target: Target, preview?, phases?: [{id, title, progress, blocked_by?}]}`, where a phase's `progress` is a line of text. `ready` (at most 15) and `active` are in work order (see Rank), so the ready list goes by phase schedule, then rank. `item` is the ItemView plus `target: Target` (where its work lands: its plan's target, or integration), `preview?` (its plan's preview URL, which serves that target), `shared?` (its plan's shared globs: the files its parallel work shares, which `done` flags; see `plan shared`), `phase_title?`, `phase_summary?`, `phase_doc?` (its phase's doc), `plan_rules?` and `phase_rules?` (its plan's and its phase's rules, in full; when either is there, `protocol` ends with a line saying to follow them, the plan's then the phase's), `open_questions?`, `queue?` (queued items in its area or tagged to its phase), `item_decisions?`, `last_report?`, `last_report_passed?` |
| `check` | `{tree, commit, at, by, passed, results: [{command, exit, duration_ms, tail?}], cached}`. The commands are config's `done_checks`; with `--item <id>`, they're what `done` runs for that item: config's, then its plan's `checks` (any already in config's left out). `cached` is `true` when a pass for the same tree and the same commands was reused. No commands to run is `no_checks` |
| `done` | `{report: Report, report_path, item: ItemView, landed, merged, merge_error?, pruned?: [], review_entry?, warnings?: [], reminder?}`. `--summary` (one line) and `--rules` (`none`, or which rules the work touched and how) are required; `--slowed`, `--covers <ids>`, `--tour` and `--design` are optional, and only one of them can be `-` (stdin). A branch behind its target fails first with `behind_target`. done runs the hard checks once (a cached pass for the same tree is reused), then the rulebook's checks, scores risk from the diff, and: high risk (a high-risk path, a touched rule, a new connection in the map) goes to review (`review_entry`); medium (over `max_lines` or `max_files`) and low land at once (`landed`), the item done, with a look filed for medium and for sampled low work. Landed work is fast-forwarded onto its target (`merged`; `merge_error` says why not, such as a checked-out target with uncommitted changes, or a target that is the release branch); `pruned` are merged worktrees removed after. Failed checks save the report and fail with `checks_failed`; the item stays active |
| `report` | `{report: Report, text, preview?}`. `text` is the markdown rendering, with each path in the tour's steps replaced by its URL on `preview`: the item's plan's preview as it is now (absent when it has none, and then the steps read as written). `report.tour` keeps the paths. `report <phase-id>` prints the phase's integration review report, with its plan's preview |

## mull serve

`mull serve` is the human's view: a web UI of every repository on mull, on `127.0.0.1` only (port 6855 unless `--port`). It writes mull data only as the human, through `POST /api/projects/{id}/ops` and only the ops its pages offer; otherwise the only thing it writes is its own last-looked state. On macOS, `mull serve --install` runs it at login as a LaunchAgent (`~/Library/LaunchAgents/mull.serve.plist`, logging to `~/Library/Logs/mull-serve.log`), restarted if it stops, with the PATH and XDG_CONFIG_HOME it was installed with; run it again after upgrading mull, and `--uninstall` to remove it.

Repositories are found with no configuration. After every command, mull adds the repository it ran in to the registry, if it has a mull branch: `~/.config/mull/repos` (or `$XDG_CONFIG_HOME/mull/repos`), one main-worktree path per line, kept per machine and never on the mull branch. A repository whose main worktree is in the system's temporary directory (`$TMPDIR`, `/tmp`, `/private/tmp` or `/var/folders`, compared as given and with symlinks resolved) is never added this way, so scratch and test repositories stay out of `mull serve`. `mull unregister [<path>]` takes a repository off (any later command run in it adds it again); `mull serve` drops it on its next read of the registry. Lines can also be removed by hand; blank lines and lines starting with `#` are skipped.

What changed since the human last looked is clouded in the UI. The last look is kept per machine, never on the mull branch: `~/.config/mull/seen.json` (beside the registry), `{repos: {<path>: {commit, at, acked?: [{type, id, commit}]}}}`, the mull branch commit last marked seen and when, and the records the human has acted on from the page since, each with the commit that acted; replaced atomically on every write. Marking seen empties `acked`. The first time `mull serve` reads a repository (or when its last look names a commit the repository doesn't have), the tip becomes the baseline, so only changes from then on are clouded. A revision is `{commit, number, at}`: `number` counts the commits on the mull branch up to `commit`, so it grows with every write, and `at` is its commit time. A Change is one record that differs between the last look and the tip, its records compared as read (so a change of storage format alone, as `mull migrate` makes, is no change): `{type ("plan"|"plan_doc"|"plan_rules"|"phase"|"phase_doc"|"phase_rules"|"item"|"entry"), id, title, plan?, phase?, kind?, change ("added"|"changed"|"removed"), state?, fields?: [{field, from?, to?}], at}`. A doc is its own record, and so are rules (`id` is its plan's slug or phase's ID, `title` its plan's or phase's). `state` is the record's state now: an item's stage, a plan's state, an entry's settle action or `"open"`. `fields` lists what changed on a changed record, with `from` and `to` for short fields (`state`, `title`, `plan`, `phase`, `claim` (the worktree), `settled`, `needs` (comma-separated), a plan's `shared` (space-separated), an integration review's `phase` and `items` (comma-separated)…) but not for text (`notes`, `summary`, `text`, `detail`, a plan's `checks`). `at` is the newest commit since the last look that touched it; changes are listed newest first. A record in `acked` is left out (what the human did isn't news to them) unless it changed again after the commit that acted; then its whole change since the last look is listed. In `GET /api/projects`, each readable project also has `revision: {number, changes, seen_at}`: the tip's number, how many records changed since the last look, and when that was.

Writes (`POST`) must be JSON (`Content-Type: application/json`, else 415 `not_allowed`) and must not come from another site (an `Origin` other than the server's own, or a `Sec-Fetch-Site` other than `same-origin` or `none`: 403 `not_allowed`), so a web page elsewhere can't post a form to it. `curl` with the JSON header is fine. A write's status follows its code: 400 `invalid_argument` or `batch_invalid`, 403 `not_allowed`, 404 `not_found`, 409 `conflict`, 503 `busy`.

Its JSON API answers only requests addressed to `localhost` or `127.0.0.1` (others get 403 `not_allowed`); errors are the same `{code, error}` objects, and an unknown endpoint is 404 `not_found`.

Derived from git each time, never stored. An item's work branches (`branches`) are its claim's branch, when that's a local branch other than a target, the release branch or `mull`, and its other unmerged branches named `<id>-…`; an item with none isn't read. A branch's changes run from its merge base with the item's plan's target to its tip, so what it took in from the target (a rebase, a merge) isn't counted; or from the claim's base when that is later or isn't on the target (work started on another branch). Renames count both paths. `view` shows each as an `overlap` problem.
- `Agent`: `{id, title, plan?, phase?, phase_title?, claim?: Claim, commits, branches?, last_activity?}`: an active item, with its linked commits (landed and not).
- `ProblemRow`: `{kind, item, text, title, state, plan?, plan_title?, phase?, phase_title?}`: a problem as `view` gives it (any kind but `overlap`), with its item's title and stage and where it sits. Derived each time, never stored.
- `ItemRow`: `{id, title, state, ready?, kind?, category?, source?, plan?, phase?, phase_title?, claim?, questions, position?, created, updated}`: an item without its notes; `questions` counts its open questions. Lists are in rank order (see Rank): open work first by rank, then done and dropped, unranked last, oldest first; the backlog has its own order. `position` is an open ranked item's place in its group's order, from 1, one more than the open items ranked before it (so equal ranks share one); finished and unranked items have none.
- `Counts`: `{unplanned, backlog}`: the project's tab counts.
- `DocRef`: `{id, type ("phase"|"item"), title, state, progress?, questions}`: a phase or item the doc (or the rules) names by ID, in order of first mention, with its status (a phase's `done`/`awaiting-review`/`now`/`waits`, an item's stage): docs hold intent, and status shows beside them.

## Batch

`mull batch` reads JSON Lines on stdin (or from a file), one op per line:

```
{"op": "<op>", "ref": "<optional name>", ...fields}
```

- **Field names are the command's flag names exactly.** Positional arguments use the names below. List fields take an array, or one string of IDs separated by commas or spaces.
- **`ref`** names the record a line creates. A later line can write `"@name"` in any ID field (`id`, `ids`, `plan`, `phase`, `item`, `needs`) to mean that record.
- **All or nothing.** Every line is validated and run in one transaction. If any line fails, nothing is written, and the error lists every failed line. A batch that passes is a single commit.
- **`--dry-run`** runs every line, writes nothing, and prints the results. IDs in a dry run's results are throwaway.

| op | fields |
|---|---|
| `plan new` | `slug`, `title`, `summary`, `target` (`own` for `plan/<slug>`, `none`, or a branch; the command defaults to `own`, the op to none), `on-request` (required: only the human creates a plan) |
| `plan agree` | `slug`, `on-request` (required: only the human agrees a plan) |
| `plan close` | `slug` |

## Migrating to Model v2

Data from before Model v2 is **format 1** (`config` shows `format: 1`). mull reads it correctly, but refuses every write with `migration_required` until it is migrated. `mull migrate --dry-run` (add `--text` to show the human) prints exactly what would change and writes nothing. The real run is the human's call: `mull migrate --on-request`, which fails with `not_allowed` without the flag. It writes one commit, and run again it changes nothing. It:

- **rewrites the format:** phases move from `epics/` to `phases/` (their docs from `docs/epics/` to `docs/phases/`, keeping their `--log` history), items store their stage and phase under Model v2 names, a done plan is stored as `done`, and config records `format: 2`;
- **captures loose ends and inbox ideas:** each open or parked one becomes a captured item of kind `idea` (title, `detail` as notes, `source`, its plan, `from` the entry), and the entry is settled `do`, pointing at it. Re-kind the bugs among them with `mull set <id> kind bug`. Settled ones stay as they are;
- **converts needs:** a phase's need on an item becomes a need on that item's phase, or is dropped when the item is done or dropped, has no phase, is in the same phase, or the need would make a cycle. Items' needs are dropped, and an unfinished item keeps them in its notes;
- **on the first migration only:** retires the standing `general` plan (it becomes `done`, its items unplanned and its entries project-wide; a `general` plan with phases stays as it is, with a warning), and gives each plan and phase with a `summary` and no doc a doc stub holding the summary (the summary stays).

Records in format 1 that reach migrated data later, merged in by `sync` from a machine still on an older mull, block writes again with `migration_required`; `mull migrate` converts them.
